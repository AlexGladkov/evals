# MANIFEST — LLM Coding Evals

Дата фиксации: 2026-11-21. Статус: договорённости зафиксированы, код ещё не пишется.

## Цель

Набор маленьких стандартизированных задач для сравнения LLM-моделей в реальных
задачах разработки. Прогон через OpenCode. Результат — стандартизированные
протоколы, которые складываются в таблицы и графики. Конечное использование —
контент (ролики/статьи), поэтому важны честность, наглядность и воспроизводимость.

## Главные принципы

1. **Одинаковые условия для всех.** Одна фикстура, один harness (OpenCode), один
   промпт, одни права и таймауты. Меняется только модель.
2. **Спека ≠ проверки.** Модель видит только условие задачи. Скрытые тесты и
   рубрики живут отдельно и моделям не передаются — иначе мерим хитрость, а не умение.
3. **Минимум 3 попытки на связку (модель × задача × язык).** Один прогон — лотерея.
4. **Задачи авторские.** Не брать известные баги из опенсорса — модели могли их
   видеть при обучении (контаминация).
5. **Правила и веса баллов фиксируются ДО прогонов.** Не подкручиваем под красивый результат.
6. **Язык — переменная.** Одна каноническая спека задачи, фикстуры — порты на каждый язык.
   Сравниваем «модель X на языке Y»; разница между языками — отдельный вывод, не артефакт.
7. **Изоляция ветками + уборка.** Каждый прогон — в отдельной git-ветке; все тесты
   проходят в ветке прогона. После отчёта рабочая копия и ветка удаляются
   (остаются протокол, дифф, логи).

## Матрица

- **Задачи:** по 5 на категорию, конкретный состав обсуждается (начали с C1).
- **Категории:** кодинг (C), архитектура (A), devops (D), секьюрити (S) — по 5 задач.
- **Языки:** Kotlin, Go, Java, Python, Rust, TypeScript (6). Старт пилота — Kotlin.
- **Фикстуры:** проекты лежат в `source/`; на старте — реальный nicehash (Kotlin).
  Порты на остальные языки — по мере необходимости.
  Нюанс: devops-задачи (Docker/CI) во многом язык-нейтральны — их фикстуры могут
  быть общими на все языки (меняется только собираемое приложение). Реальное число
  фикстур будет меньше 100.
- **Повторы:** ≥3 на связку.
- **Порядок:** пилот на кодинг-наборе (C1–C5), остальные категории достраиваем после.
- Полный масштаб: 20 задач × 6 языков × 4–5 моделей × 3 попытки — большой,
  выпускаем порциями (категория за категорией), а не одним марафоном.

## Задачи

4 категории × 5 задач. Конкретные задачи обсуждаем по одной и фиксируем здесь
после согласования. Каждая задача должна бить в типичную слабость LLM.

Принципы проверки по категориям:
- **Кодинг (C1–C5):** скрытые тесты с edge-случаями; проверяем семантику
  (поведение), а не точные байты вывода — верных реализаций может быть несколько.
- **Архитектура (A1–A5):** следование подходу проверяется МЕХАНИЧЕСКИ
  (дифф файлов, граф зависимостей, использование интерфейсов), а не «на глаз».
- **DevOps (D1–D5):** реальный запуск сборки/контейнера/пайплайна. Бинарно.
- **Секьюрити (S1–S5):** скрытые тесты-АТАКИ (вредоносный запрос → отказ),
  обычные тесты при этом проходят.

### Согласованные задачи

**C2 — Багфикс «NaN в доходе» (реальный проект nicehash, Kotlin).**
Фикстура: `source/nicehash/` (снапшот приватного проекта, коммит `b8fcbd7`,
санитизирован — см. PROVENANCE.md). Язык один: Kotlin/Android — в матрицу 5 языков
не входит, это задача категории «реальный проект» внутри кодинг-набора.

Тикет: «У нового майнера без статистики экран дохода показывает NaN. Почини.
Заодно месяц должен считаться по реальному числу дней, а не всегда 31».

Требования:
- пустые данные → нули, никаких NaN/Infinity;
- нулевая скорость не ломает расчёт;
- месяц = реальное число дней текущего месяца;
- поведение на нормальных данных не менять (кроме пункта про месяц);
- интерфейс репозитория и презентер не трогать.

Проверка: JVM unit-тесты без эмулятора (фейковый провайдер → `fetchMinerIncome`):
пустые данные, нулевая скорость, регрессия на нормальных данных, дни месяца.
Механически: презентер и интерфейс не изменены.
Что проверяем: диагностика (найти две причины самой), дисциплина bugfix
(починить причину, не переписав проект), следование ограничениям.

**C1 — Фича «Годовой доход на экране Income» (nicehash, Kotlin) — предварительно согласована.**
Реальный пробел: KDoc обещает период «year», но его нет в модели/расчёте/UI.
Тикет: добавить год по образцу существующих периодов (час/день/неделя/месяц).
Требования: поля `yearBtc`/`yearValue` в `Income`; расчёт = средний дневной доход ×
реальное число дней текущего года (365/366); конвертация в презентере через
`exchangeServer` по образцу; строка в layout + ресурс `income_year`;
существующие периоды и тесты не ломать.
Проверки: JVM-тесты расчёта (фейковый провайдер) + регрессия старых полей;
механически — строка в layout и ресурс существуют, сборка проходит.
Что проверяем: навигация по настоящему коду, следование паттерну «допиши по образцу».

**C3 — Полная миграция nicehash Kotlin → Java (предварительно согласована).**
Спека: `tasks/coding/java/c3.md`, проверки: `checks/coding/java/c3.md`.
Объём: модуль app (150 .kt), Compose-экраны → XML, kapt → annotationProcessor,
тесты переводятся. Benchmark-модули вне объёма (Kotlin-only API).
Поведение сохраняется, баги оригинала не чинятся (fidelity).
Метрика: доля готовности (completion/build/tests), не бинарный зачёт —
полная миграция слишком велика для «всё или ничего».
Что проверяем: владение Java, миграция легаси, выносливость на длинной задаче,
дисциплина (не выкидывать фичи ради сборки).
Языки-альтернативы отвергнуты: Rust/Go/Python на Android — только NDK/эксперименты,
полноценное приложение не собрать; Flutter/RN — стройка с нуля, не миграция.

**C4 — Тесты на легаси: расчёт дохода (nicehash, Kotlin) — согласована.**
Спека: `tasks/coding/kotlin/c4.md`, проверки: `checks/coding/kotlin/c4.md`.
Тикет: покрыть unit-тестами логику расчёта дохода, продакшен-код не менять.
Главная метрика — **mutation score**: 16 заранее подготовленных мутантов
(поломок кода), тесты модели обязаны падать на них. Полезность тестов
измеряется числом убитых мутантов, а не фактом наличия тестов и не coverage.
Анти-читерство: тавтологии, тесты моков, проглатывание исключений — штрафы.
Бонус: @Ignore-тесты, вскрывающие реальные баги (NaN, деление на ноль).
Что проверяем: умение тестировать чужой код, понимание поведения, честность тестов.

C5 — обсуждается (кандидаты: интеграция с внешним API через MockWebServer,
порт модуля расчёта на Rust, конкурентная загрузка).

## Формат спеки задачи (то, что видит модель)

1. **Цель** — одна строка.
2. **Дано** — что уже есть в проекте.
3. **Требования** — список «когда X → должно Y».
4. **Ограничения** — что нельзя трогать/менять.
5. **Ожидаемый результат** — 1–2 базовых примера вход→выход + критерий «готово».

Хитрые случаи в примерах НЕ показываем — они остаются в скрытых тестах.

## Метрики и протокол прогона

Каждый прогон порождает два файла из одного источника (автоматически):
- **JSON** — машинный протокол со строгой схемой (для агрегации и графиков).
- **Markdown** — короткая выжимка для человека и контента.

Поля протокола (черновик схемы):
- модель, задача, язык, № попытки, дата, версия фикстуры/спеки;
- gate: сборка ок, скрытые тесты (пройдено/всего), существующие тесты не сломаны;
- качество: балл по рубрике (костыли, размер диффа, следование ограничениям);
- эффективность: время, входные/выходные токены, цена;
- скорость: выходные токены/сек — **отдельно от баллов качества** (это скорость
  провайдера, зависит от нагрузки и времени суток; для честности — прогоны в одно время);
- вердикт: зачёт/незачёт + причина.

Итоговый балл = gate-баллы + качество (штрафы) + экономность (токены).
Скорость (ток/сек) в зачёт не входит — показывается отдельно.
Точные веса — зафиксировать до первого прогона (открытый вопрос).

## Структура проекта

```
evals/
  AGENTS.md            # правило стиля общения
  MANIFEST.md          # этот файл — договорённости
  source/              # проекты для экспериментов (напр. source/nicehash/)
  tasks/               # спеки задач (видят модели)
    coding/ architecture/ devops/ security/
      kotlin/ go/ java/ python/ rust/ typescript/   # спеки по языкам
  checks/              # скрытые проверки и рубрики (моделям НЕ давать),
                       # зеркалит структуру tasks/
  runs/<дата>/<модель>/<задача>-<язык>-<попытка>.json|.md
  scripts/             # раннер и агрегатор (позже)
```

## Процесс прогона (целевой)

1. Раннер копирует фикстуру в изолированную рабочую папку, инициализирует git
   и создаёт **отдельную ветку прогона** (`run/<модель>/<задача>/<попытка>`).
2. Запускает OpenCode (`opencode run`, неинтерактивно, auto-approve, таймаут)
   с моделью-параметром и спекой задачи. Модель работает в своей ветке.
3. После прогона подкладывает скрытые тесты, запускает gate-проверки
   **в этой же ветке**. Все тесты (видимые + скрытые) должны проходить в ветке
   прогона — ветки изолированы, прогоны не влияют друг на друга.
4. Собирает логи сессии (токены, время, шаги), считает метрики, сохраняет
   дифф ветки как артефакт.
5. Пишет протокол JSON + MD в `runs/`.
6. **Уборка после отчёта:** рабочая копия и ветка прогона удаляются, остаются
   только протокол, дифф и логи. Причина: сотни прогонов не должны забивать диск
   и мешать друг другу; отчёт + дифф — достаточное свидетельство результата.
7. Агрегатор (отдельный скрипт) складывает протоколы → таблицы/графики.

- [ ] Язык спек (русский/английский) — не решено.
- [ ] Таймаут прогона и лимиты (токены/шаги) — не решено.
- [ ] Список моделей для первого сравнения и бюджет.
